A remote machine is one you don't have physical access to. It may sit in a lab or a cloud provider's data center, so you can't simply walk up to it.
Accessing such a machine is called remote access. Common methods include SSH, VNC, and RDP.

## 1. Protocol layer: how many are visible on the internet (Shodan)

| Port/protocol | Internet-facing hosts | Main implementations |
|---|---|---|
| 22/SSH | 19,505,811 | OpenSSH 16,512,713 (~85%), Dropbear 367,746 (~2%, mostly routers and embedded devices) |
| 3389/RDP | 2,250,757 | 1,662,670 identified as RDP |

- Only services exposed to the internet on default ports are counted. Internal hosts and hosts on non-default ports are excluded, so treat these as relative magnitudes.
- On servers, SSH is effectively OpenSSH. Windows has also shipped OpenSSH since Windows 10 1809.
- RDP is built into Windows, so its real usage tracks the Windows install base. Internet-exposed RDP has long been a leading ransomware entry point.

## 4. Trends

- **No more ports opened directly to the internet**: SSH and RDP themselves remain, but the entry point is moving to zero trust gateways or bastion hosts, with identity-based access control.
- **Remote support vendors are becoming platforms**: TeamViewer now leads with TeamViewer ONE / DEX rather than plain remote control, and partners with ServiceNow on IT operations ([TeamViewer IR](https://ir.teamviewer.com/websites/teamviewer/English/1/investor-relations.html)).
- **Server out-of-band management**: largely handled by BMC plus Redfish, a separate market from SSH/RDP.

A bastion host focuses on centralized login and auditing for operations staff; a zero trust gateway focuses on hiding network entry points and authorizing each access by identity.

## Bastion host (jump server / privileged access auditing)

Operators cannot SSH or RDP to servers directly. They log in to the bastion host first, and the bastion connects to the target on their behalf.

```
Operator ──SSH/RDP/Web──> Bastion ──SSH/RDP/DB protocol──> Target server
                          │
                          ├─ Authentication: account + MFA
                          ├─ Authorization: Alice may only log in to web01, and only as a non-root account
                          ├─ Credential vault: target passwords/private keys stay on the bastion, hidden from users
                          ├─ Audit: session recording and command logs, replayable
                          └─ Control: block dangerous commands (e.g. rm -rf /), approvals, time windows
```

- **Role**: a single entry point plus auditing. The original "bastion host" was a hardened jump box in the DMZ. In China, "bastion" usually means a full privileged-access auditing product, often deployed to meet MLPS (Multi-Level Protection Scheme) audit requirements.
- **Representative products**: JumpServer (open source), Qizhi, CyberArk PAM, BeyondTrust. Cloud offerings such as Azure Bastion and AWS Session Manager are lighter: they broker connections but don't do fine-grained auditing.
- **Prerequisite**: users usually still reach the bastion through a VPN or the internal network. The bastion itself is a fixed entry point, so a compromise has a large blast radius.

## Zero trust gateway (ZTNA)

The core principle of zero trust is "never trust, always verify": being on the internal network does not make a user trusted, and every access re-checks identity and device posture.

```
User device ──> Zero trust gateway / control plane ──(reverse connector, outbound tunnel)── Internal app
                │
                ├─ Identity: SSO (Okta/AAD) + MFA
                ├─ Device: company-managed? patched? EDR installed?
                ├─ Context: location, time, risk score
                └─ Policy: grant access to a specific app, not a whole subnet
```

- **Versus VPN**: once connected to a VPN, the whole internal subnet is reachable, so an attacker can move laterally. ZTNA grants access to one application only; the rest of the network stays invisible.
- **Apps are not exposed**: internal apps attach to the gateway through outbound connectors, so ports 22 or 3389 never need to be opened to the internet and scanners can't find them.
- **Continuous verification**: the session can be cut at any time if device posture or risk changes.
- **Reference architecture**: NIST SP 800-207 splits it into a Policy Decision Point (PDP), which decides whether access is allowed, and a Policy Enforcement Point (PEP), the gateway that allows or blocks traffic.
- **Representative products**: Google BeyondCorp, Cloudflare Access, Zscaler Private Access, Palo Alto Prisma Access, Tailscale, Teleport.

## Comparison

| | VPN | Bastion host | Zero trust gateway |
|---|---|---|---|
| Trust model | Trusted once on the network | Access by permission once on the bastion | Every request re-verified |
| Authorization granularity | Subnet | Host + account | Application / resource |
| Exposed ports | VPN port | Bastion port | Essentially none (outbound tunnel) |
| Device posture check | Weak | Usually none | Yes |
| Audit | Weak | Strong (recording, commands) | Access logs; some products record sessions |
| Main use | Employees joining the internal network | Operators managing servers | Employees / contractors reaching internal apps |

## How they relate

They are not mutually exclusive and are converging. A common setup uses a zero trust gateway in place of the VPN to decide whether someone can get in, and a bastion host to govern what they can do and record what they did. Products like Teleport and StrongDM do both: identity-driven access with no exposed ports, plus SSH/RDP/database session recording and short-lived credentials.
