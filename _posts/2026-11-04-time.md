## `cron vs sched vs schedule`

| | cron | `schedule` (pip 包) | `sched` (标准库) |
|---|---|---|---|
| **本质** | OS 守护进程，fork 子进程 | Python 进程内轮询循环 | Python 进程内事件队列 |
| **运行方式** | 常驻后台，到点 fork | 常驻 Python 进程，忙轮询 | 常驻 Python 进程，阻塞等待 |

### 资源消耗对比

| 维度 | cron | `schedule` (pip) | `sched` (stdlib) |
|---|---|---|---|
| **空闲 CPU** | ~0（每分钟唤醒一次） | ~0（sleep 1s，但频繁唤醒） | **~0**（精确 sleep 到事件） |
| **内存** | 2-5 MB (crond) + 每任务临时进程 | 10-20 MB (Python 进程) | 10-20 MB (Python 进程) |
| **任务执行开销** | fork+exec ~5-50ms | 函数调用 ~μs | 函数调用 ~μs |
| **精度** | 分钟级 | 秒级（= sleep 间隔） | 毫秒级 |
| **轮询方式** | 每分钟检查 | **忙轮询**（固定间隔 sleep+check） | **精确等待**（sleep 到事件时刻） |
| **周期性** | 原生支持 | 原生支持 | 不支持（需手动重新 enter） |
| **持久化** | ✅ crontab 文件 | ❌ 进程退出即丢失 | ❌ 进程退出即丢失 |
| **任务隔离** | ✅ 进程级 | ❌ 需自己 try/except | ❌ 需自己 try/except |
| **并发** | ✅ 多进程并行 | ❌ 串行（除非自己加线程） | ❌ 串行 |
| **依赖** | OS 自带 | `pip install schedule` | Python 标准库 |

### 1. cron

cron 由一个常驻后台守护进程 `crond` 实现，核心逻辑：

```
while true:
    检查 crontab / var/spool/cron 中的任务表
    若当前时间匹配某任务的 cron 表达式 → fork + exec 该任务
    sleep 到下一分钟
```

- **触发方式**：`crond` 每分钟唤醒一次（`sleep`），比对时间字段。
- **精度**：分钟级（最小粒度 1 分钟）。
- **进程模型**：每次触发都 `fork()` 一个新进程执行任务，任务之间相互隔离。
- **不阻塞**：`crond` 不关心任务执行多久，到点就起新进程。
- **优点**：空闲时几乎零开销，任务隔离好，持久化。
- **缺点**：每次任务 fork 新进程，启动开销大；最小粒度 1 分钟。

### 2. `sched`

`sched.scheduler` 是一个**单线程事件队列**：

```python
import sched, time
s = sched.scheduler(time.time, time.sleep)
s.enter(10, 1, print, ("hello",))  # 10秒后执行
s.run()  # 阻塞，直到队列空
```

`run()` 内部：

```
while 队列非空:
    取出最早的事件
    delay = event.time - now
    if delay > 0: time.sleep(delay)   # 阻塞等待
    执行 event.action()
```

- **触发方式**：`time.sleep(delay)` 阻塞到目标时刻。
- **精度**：取决于 `time.sleep` 的精度，通常毫秒级，比 cron 高得多。
- **进程模型**：单进程、单线程，事件在同一个解释器里顺序执行。一个事件阻塞会推迟后续所有事件。
- **一次性**：`enter` 注册的事件执行一次即移除，不像 cron 周期性触发（需自己重新 `enter` 实现循环）。
- **要点**：`sched` **不轮询**。它计算到下一个事件的精确延迟，然后 `sleep` 那么久。没有忙等待，精度由 `time.sleep` 决定（毫秒级），CPU 占用极低。

### 3. `schedule`

```python
import schedule, time

def job():
    print("hello")

schedule.every(10).seconds.do(job)

while True:
    schedule.run_pending() # 遍历所有任务
    time.sleep(1)    # ← 轮询间隔
```

```
Python 进程常驻
  → while True 循环
  → 每次循环: time.sleep(1) 阻塞 1 秒
  → 唤醒后 run_pending() 遍历所有任务检查是否到期
  → 到期则在当前线程直接调用 job()
  → 继续循环
```

**要点**：`schedule` 是**忙轮询**。`time.sleep(1)` 意味着：
- 最坏情况下任务延迟 1 秒才被执行（精度 = sleep 间隔）。
- 缩小 sleep 间隔（如 `sleep(0.01)`）可以提高精度，但 CPU 占用上升（频繁唤醒 + 遍历任务列表）。

### 4. 真正的"中断方式"

> 内核定时器（`clock_nanosleep` / `timerfd`）最终是硬件中断驱动的

**中断驱动**的定时调度，对应的是：

- **信号**：`signal.SIGALRM` + `signal.alarm()` / `setitimer`，内核到点发信号中断当前执行流。
- **硬件中断 / ISR**：嵌入式或内核态，由硬件定时器直接触发中断服务程序。
- **asyncio**：事件循环 + `call_later`，虽然是协作式调度，但回调是被事件循环"唤醒"执行，更接近中断语义（回调打断当前协程的等待状态）。

```python
# 信号方式（真正的中断）
import signal
def handler(signum, frame):
    print("被中断触发")
signal.signal(signal.SIGALRM, handler)
signal.alarm(5)  # 5秒后内核发SIGALRM中断主流程
```

### 选型建议

```
需要持久化 + 进程隔离 + 分钟级精度？
  → cron

Python 进程内，周期性任务（每 N 秒/分钟重复）？
  → schedule（API 友好，天然支持周期）

Python 进程内，一次性定时 / 精确调度 / 大量任务？
  → sched（无轮询开销，精度高）

需要并发执行 + 进程内？
  → threading.Timer 或 asyncio.call_later
```

## time 时间来源

Python `time` 模块调用的是操作系统（libc）的时间系统调用，操作系统内核内部去读硬件时钟源（HPET/TSC/ACPI PM Timer 等）。

### 调用链

```
Python time.time()
  → CPython C 层: time_time() (Modules/timemodule.c)
    → libc: clock_gettime(CLOCK_REALTIME)  [Linux] / GetSystemTimeAsFileTime() [Windows]
      → Linux 内核: sys_clock_gettime()
        → 读取硬件时钟源 (clocksource)
          → TSC (首选) / HPET / ACPI PM Timer
```

每一层各司其职：

#### 第 1 层：CPython（用户态库代码）

`time.time()` 在 CPython 源码 `Modules/timemodule.c` 中就是一个薄封装：

```c
// CPython Modules/timemodule.c (简化)
static PyObject *
time_time(PyObject *self, PyObject *unused)
{
    return _PyTime_AsSecondsDouble(_PyTime_GetSystemClock());
    // _PyTime_GetSystemClock → clock_gettime(CLOCK_REALTIME) 或 gettimeofday()
}
```

`time.perf_counter()`、`time.monotonic()` 类似，只是换一个 clock id：

| Python 函数 | 底层系统调用 (Linux) | clock id |
|---|---|---|
| `time.time()` | `clock_gettime(CLOCK_REALTIME)` | 墙上时钟，可跳变（NTP 调整） |
| `time.monotonic()` | `clock_gettime(CLOCK_MONOTONIC)` | 单调时钟，不受 NTP 影响 |
| `time.perf_counter()` | `clock_gettime(CLOCK_MONOTONIC)` (最高精度) | 同上，含 sleep 时间 |
| `time.process_time()` | `clock_gettime(CLOCK_PROCESS_CPUTIME_ID)` | CPU 时间 |

Windows 上对应的是 `QueryPerformanceCounter`（`perf_counter`）、`GetTickCount64`（`monotonic`）、`GetSystemTimeAsFileTime`（`time`）。

### 第 2 层：Linux 内核（系统调用）

内核 `sys_clock_gettime()` 根据 clock id 选择对应的 `struct clocksource`，调用 `->read()` 读取硬件：

```c
// Linux kernel kernel/time/timekeeping.c (简化)
static u64 read_clock_counter(const struct clocksource *cs) {
    return cs->read(cs);  // 调用具体硬件驱动的读函数
}
```

### 第 3 层：硬件时钟源

内核通过 `clocksource` 框架抽象多种硬件，**优先选精度最高、开销最低的**：

```
$ cat /sys/devices/system/clocksource/clocksource0/current_clocksource
tsc          # 现代 x86 几乎总是 TSC
```

| 硬件时钟源 | 位置 | 精度 | 现代状态 |
|---|---|---|---|
| **TSC** (Time Stamp Counter) | CPU 内部寄存器，`rdtsc` 指令 | 纳秒级，~1 cycle 读取 | **首选**，invariant TSC 后已稳定 |
| **HPET** (High Precision Event Timer) | 主板芯片组 (ICH/PCH) | 纳秒级，但读取慢 (~1-2μs) | 备选/降级方案 |
| **ACPI PM Timer** | 主板 | ~3.58MHz (~279ns) | 老旧系统备选 |
| **jiffies** | 内核软件计数器 | 毫秒级 (HZ=250/1000) | 仅低精度场景 |

查看当前时钟源和可用列表：

```bash
cat /sys/devices/system/clocksource/clocksource0/current_clocksource   # tsc
cat /sys/devices/system/clocksource/clocksource0/available_clocksource  # tsc hpet acpi_pm
```

### 为什么不是 HPET

现代 x86 系统（约 2010 年后，invariant TSC 普及后）几乎都用 **TSC** 而非 HPET：

- **TSC** 在 CPU 内，`rdtsc` 是一条指令，~20-40 周期（~10ns），无需跨总线访问芯片组。
- **HPET** 在 PCH（芯片组）上，读取要走 MMIO 总线，开销 ~1-2μs，比 TSC 慢 100 倍。
- invariant TSC 解决了旧 TSC 的痛点（频率漂移、每核不一致、C-state 停止），使 TSC 成为可靠时钟源。

HPET 现在主要用作**定时器中断源**（`hpet` 作为 `clock_event_device`，驱动 `timerfd` / `setitimer` 的到期中断），而非 `clock_gettime` 的读取源。

### 完整图景：读时间 vs 定时中断

```
┌─────────────────────────────────────────────────┐
│  读时间 (time.time / perf_counter)               │
│    Python → clock_gettime → 内核读 TSC (rdtsc)   │
│    纯查询，无中断，无硬件定时器到期               │
└─────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────┐
│  定时等待 (time.sleep / sched / cron)            │
│    Python → nanosleep → 内核 hrtimer             │
│    内核设硬件定时器 (HPET/LAPIC Timer) → 到期中断 │
│    ← 这里才有真正的硬件中断                       │
└─────────────────────────────────────────────────┘
```

- **读时间**（`time.time()`）：查询 TSC 寄存器，**无中断**，纯 CPU 指令。
- **定时等待**（`time.sleep()`）：内核设一个 hrtimer，到期后由 **HPET 或 Local APIC Timer 产生硬件中断**唤醒进程。

## 系统时钟

操作系统在内存（RAM）中维护一个软件时钟（`xtime`/`tkr`），每次需要时用 TSC 做增量计算。CMOS/RTC 只在**关机/断电时**持久化一个粗略值，开机时读取一次作为初始值，之后就不参与了。

### 完整链路

```
┌─────────────────────────────────────────────────────────────┐
│  断电持久化层                                                 │
│  ┌─────────────┐                                            │
│  │ CMOS / RTC  │  主板纽扣电池供电，64字节RAM区              │
│  │ (MC146818)  │  存: 年月日时分秒 (BCD编码, 秒级精度)        │
│  └──────┬──────┘                                            │
│         │ 仅在开机时读一次 (内核 boot 阶段)                   │
│         ▼                                                    │
│  ┌─────────────────────────────────────────────────────────┐│
│  │ 内核内存中的软件时钟 (运行时唯一权威)                     ││
│  │                                                         ││
│  │  tk_core.tk_raw  ← 墙上时钟的"基准时间戳" (CLOCK_REALTIME)││
│  │  tkr.cycle_last  ← 上次校准时的 TSC 读数                 ││
│  │  tkr.mult/skip   ← 换算系数 (cycles → ns)               ││
│  │                                                         ││
│  │  读取时: now = tk_raw + (rdtsc - cycle_last) * mult      ││
│  │         ↑ 不读任何硬件时钟寄存器获取"绝对时间"            ││
│  │           只读 TSC 做增量                                ││
│  └─────────────────────────────────────────────────────────┘│
│         ↑ NTP 同步修改的是 tk_raw 和 mult (微调)             │
│         │                                                    │
│  ┌──────┴──────┐                                            │
│  │  NTP / PTP  │  周期性校准，调整内核软件时钟                │
│  │  chronyd    │  (不写 CMOS，除非手动 hwclock --systohc)    │
│  └─────────────┘                                            │
└─────────────────────────────────────────────────────────────┘
```

### 各层详解

#### 1. CMOS / RTC（断电持久化）

- **硬件**：MC146818 兼容 RTC 芯片，集成在 PCH（芯片组）中，主板纽扣电池（CR2032）供电。
- **存储内容**：64 字节 CMOS RAM，前 14 字节存日期时间（BCD 编码，秒级精度）。
- **角色**：**仅在开机时被内核读取一次**，作为初始墙上时钟值。之后内核不再依赖它维持运行时时间。
- **精度**：秒级，且晶振漂移大（~几十 ppm），不适合运行时计时。

```bash
# 查看硬件时钟（CMOS/RTC）当前值
hwclock -r          # 或 timedatectl
```

#### 2. 内核软件时钟（运行时权威）

Linux 内核在内存中维护时间，核心结构在 `kernel/time/timekeeping.c`：

```c
// 简化示意
struct timekeeper {
    struct tk_read_base tkr;  // 时钟源读取基线
    u64 raw_time;             // CLOCK_MONOTONIC_RAW 基准
    // ...
};

struct tk_read_base {
    struct clocksource *clock;   // 指向 TSC clocksource
    u64 cycle_last;              // 上次校准时的 TSC 值
    u64 mask;
    u32 mult;                    // cycles → ns 换算系数
    u32 shift;
};

// clock_gettime(CLOCK_REALTIME) 的核心逻辑
u64 now_ns = tk->tkr.xtime_nsec          // 基准时间(纳秒)
           + (rdtsc() - tkr.cycle_last)   // TSC 增量
           * tkr.mult >> tkr.shift;       // 换算为纳秒
```

**关键点**：运行时获取时间 = **内存中的基准值 + TSC 增量计算**，不读 CMOS，不读 HPET。

#### 3. NTP 同步（校准软件时钟）

`chronyd` / `ntpd` 通过网络获取精确时间后，**修改的是内核内存中的 `tk_raw` 和 `mult`**：

- **小偏差**（< 500ppm）：微调 `mult`（变快/变慢），平滑收敛（adjtime 方式）。
- **大偏差**：直接 `settimeofday()` 重置 `tk_raw`（跳变）。
- **不写 CMOS**：NTP 同步默认不回写硬件时钟。

```bash
# 手动将内核时间写入 CMOS（通常由 systemd 定时自动执行）
sudo hwclock --systohc

# 查看是否启用了 NTP 同步
timedatectl status
#   NTP service: active
#   RTC in local TZ: no
```

#### 4. 关机/断电后

- 内核软件时钟随断电消失。
- CMOS/RTC 靠纽扣电池继续走时（精度差，但够用）。
- 下次开机，内核重新从 CMOS 读取初始值，再用 TSC 增量维持高精度时间。
- 如果有 NTP，开机后很快校准到精确时间。

### 对比总结

| 层 | 硬件/软件 | 存什么 | 何时参与 | 精度 |
|---|---|---|---|---|
| **CMOS/RTC** | 硬件（PCH + 纽扣电池） | 绝对日期时间 | 开机读一次；关机时维持 | 秒级 |
| **TSC** | 硬件（CPU 寄存器） | 自上电以来的 cycle 计数 | 每次读时间时做增量 | 纳秒级 |
| **内核 timekeeper** | 软件（内存） | 基准时间戳 + TSC 基线 + 换算系数 | 运行时唯一权威 | 纳秒级 |
| **NTP** | 软件（网络） | 校准基准时间戳和频率 | 运行时周期性修正 | 网络级（ms） |
